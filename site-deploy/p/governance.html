로그 거버넌스 — 데이터가 만들어지는 지점부터 책임지기

소속토스증권기간2025.08 ~ 현재역할로그 설계 · DQA · 모니터링 · 표준화
Impala · Kibana(ES|QL) · GitHub · Claude Code 스킬로그 설계 · DQA · 모니터링 · 표준화

토스증권에서 Data Governance Specialist로 일하며 제품 로그가 설계되고, 검증되고, 배포 후에도 유지되는 전 과정을 맡아 온 기록입니다. AI · 대차 · Trading · WM 네 도메인에서 같은 원칙으로 일했습니다.

🎯 핵심 결론

  • 로그 결함을 "지표가 이상하다"로 드러나기 전에 잡습니다. 설계, 검증, 이상 추적, 감시 네 지점에 각각 막는 장치를 두었습니다.
  • 대표 사례는 연금저축 런칭입니다. 명세 421행을 라이브 로그와 전수 대조해 하드 누락 0건을 확인했고, 런칭 전 QA에서는 166건 전량 미발화인 파라미터를 찾아 재설계했습니다.
  • 혼자 잘하는 일을 팀이 쓰는 자산으로 바꿨습니다. 배포 후 헬스체크는 직접 만든 스킬로, 흩어진 구양식 명세는 신표준 명세 59개로 옮겼습니다.

Background (S)

제품 로그는 분석·실험·대시보드의 원재료입니다. 로그가 틀리면 그 위의 숫자가 모두 틀리는데, 로그 결함은 대개 누군가 지표가 이상하다고 느낀 뒤에야 드러납니다. 그때는 이미 측정 공백이 생긴 뒤입니다. 사일로마다 명세 양식과 QA 깊이도 달랐고, 배포 후 로그가 깨져도 알려주는 장치가 없었습니다.

Problem (T)

❶ 늦게 드러나는 결함 — 누락과 값 오류가 분석 단계에서야 발견돼, 복구할 수 없는 측정 공백이 생김 ❷ 사일로마다 다른 방식 — 명세 양식, 네이밍, QA 깊이가 제각각이라 담당자가 바뀌면 품질이 흔들림 ❸ 사람에 의존하는 감시 — 배포 후 로그가 유지되는지는 담당자가 그때그때 쿼리를 짜서 확인

→ WHY 로그가 틀리면 그 위의 분석과 실험이 모두 틀림 / HOW 로그의 생애주기를 네 지점으로 나눠 각 지점에 막는 장치를 두고, 그 방식을 표준 문서와 도구로 남김

Work Process (A)

설계 → 검증 → 이상 추적 → 감시 → 표준화

단계 한 일 대표 근거
설계 기획 단계에서 지표와 로그를 함께 정의하고, 측정이 깨지는 상황을 미리 요건에 반영 라이브 체류시간 로그에 새로고침·작은 창 종료 등 누락 케이스 반영 / 한 경로로만 찍히던 화면에 단계 구분자를 넣어 명세 346 → 150행
검증 명세와 실제 로그를 행 단위로 대조. 런칭 전에는 알파 재현, 런칭 후에는 라이브 전수 대조 명세 421행 대조 하드 누락 0건 / 166건 전량 미발화 파라미터 적발 / 화면 이관 6개 지면 전수조사
이상 추적 있을 수 없는 숫자를 가설 단계별로 좁혀 원인을 확정하고 수정까지 연결 대차 퍼널 단계 역전 → view 누락 확정, FE 수정 / 계좌개설 UV 역전 → 진입 경로 규명, 명세 17건 정정 / 진입점 값과 UTM의 정합성 검증
감시 배포 후 헬스체크를 스킬로 자동화 모니터링 스킬 2종 직접 제작, 판정 4축(누락·볼륨·NULL률·값 변형)
표준화 흩어진 명세와 QA 방식을 전사 표준으로 정리 신표준 명세 59개 이관(PR 10건) / 7개 사일로 QA 프로세스 비교, 테스트케이스 표준 실물 / 새 로그 모델 스터디 회차 진행

일하는 방식의 전환 (2026 ~ 현재) — 처음에는 로그 설계를 노션에 손으로 쓰고, QA도 앱·웹에서 직접 로그를 찍어 쿼리로 확인했습니다. Claude Code를 쓰면서 설계부터 모니터링까지 스킬로 자동화하는 방법을 세웠고, 테스트케이스대로 DQA를 진행해 업무 효율을 높였습니다. 또 담당자(DGS)마다 손으로 심던 로그가 서로 달라 정합성이 낮았던 문제를 풀기 위해, 컬럼마다 하나의 책임을 정하는 ATM 로그 모델 거버넌스 체계를 수립하고 있습니다. JP 지면부터 현재 KR 지면까지 ATM으로 이관하고 있으며, JP 지면(의견보내기·지금뜨는산업)은 지면 리뷰 스킬로 r01~r03 리뷰 → 수정 개발 → QA 완료까지 진행했습니다. (출처: 본인 설명 2026-11, data-analysis-jp 커밋 2026-10)

대표 장면: 연금저축 대고객 런칭 (2026.07 ~ 08) — 새로 맡은 도메인에서 인수인계 4건을 받아 런칭에 대응했습니다. 노션과 md에 나뉘어 있던 명세 정본을 한곳으로 모으고, 런칭 전 알파 QA에서 ETF 섹션의 필터 파라미터가 166건 전량 미발화인 것을 찾아 재설계했습니다. 배포 후에는 명세에서 기대 로그 421행을 뽑아 라이브 로그와 전수 대조해 하드 누락 0건을 확인했습니다. 분석가가 문의한 퍼널 UV 역전은 진단 쿼리 6종으로 원인(인트로를 건너뛰는 진입 경로)을 찾아 명세 17건을 정정했습니다.

Result & Insight (R)

▸ 런칭 로그 신뢰성 — 명세 421행 전수 대조에서 하드 누락 0건. 발견탭 클릭 로그의 섹션명 부여율이 배포 전 0~1%에서 배포 후 97~98%로 올라간 것을 시간대별로 확인 ▸ 분석 전에 잡은 결함 — 대차 퍼널의 view 누락, 주문 화면의 이중 prefix, ETF 섹션의 필터 파라미터 미발화를 찾아 FE 수정으로 연결 ▸ 팀이 쓰는 자산 — 모니터링 스킬 2종, 신표준 명세 59개, "퍼널 단계 역전 3단계 검증" 같은 검증 방법을 팀 레퍼런스로 남김 ▸ 개인정보 관점의 발견 — 명세를 이관하며 지면을 하나씩 실측하는 과정에서, 화면 내용에 계좌번호와 이름이 찍히는 로그 9곳을 발견 ▸ 분석으로 연결 — 로그 구조를 알기 때문에 분석에서 0건과 역전을 그대로 믿지 않음. 연말 절세 수요 검증에서 해마다 바뀐 화면 경로를 잡아낸 것이 그 예

진입 유저수·전환율 등 사내 KPI 절대값은 제외하고, 작업 산출물(명세 행수·정정 건수·PR 수)만 기재했습니다.

🔗 연결 역량

  • 측정 설계 — 지표가 집계 가능한 형태로 로그가 남도록 기획 단계에서 정의
  • 데이터 품질 검증(DQA) — 명세와 실제 로그의 전수 대조, 알파·라이브 교차 검증
  • 근본 원인 추적 — 불가능한 패턴을 가설 단계별로 좁혀 원인 확정
  • 자동화 — 배포 후 헬스체크를 직접 만든 스킬로 도구화, 오판 방지 규칙 내재화
  • 표준화 · 협업 — 전사 명세 이관과 QA 표준 수립, FE·분석가와의 수정·정정 협업

Learning

로그 품질은 한 번의 QA로 끝나지 않고, 설계부터 배포 후까지 이어지는 관리의 문제입니다. 결함을 찾는 것보다, 같은 결함이 다음에는 사람 손을 거치지 않고도 드러나게 만드는 것이 거버넌스의 일이라는 것을 배웠습니다.
