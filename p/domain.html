신규 도메인 확장 — 공매도 프로모션 & Trading 주문 PIP 로그 QA

소속토스증권기간2026.06 ~ 2026.07역할신규 도메인 로그 QA 단독 수행
Impala · Kibana(알파·라이브) · 로그 레코더로그 QA · 버그 적발 · 신규 도메인 단독 수행

SBL을 넘어 공매도 프로모션·Trading(WTS 주문 PIP)이라는 신규 도메인의 로그 QA를 단독으로 수행하며, 라이브 배포 검증과 버그 적발·FE 수정 견인까지 책임진 도메인 확장 사례입니다.

🎯 핵심 결론

  • 타 팀에서 인계받은 Trading 주문 PIP 로그 QA를 단독 수행하며, 이중 prefix 버그를 적발해 FE 이슈레이징 → 수정 → 재QA 통과까지 견인했고, 이후 라이브 재점검에서 해소를 확인했습니다.
  • 공매도 프로모션(#6) 배포 헬스체크에서 step-4 view 100% 발화를 확인(이전 프로모션의 ~40% 누락과 대조)하고, 명세↔라이브 mismatch 8건을 반영했습니다.
  • 로그 레코더 CSV가 analytics 타입을 캡처하지 못한다는 한계를 발견해, 알파 Kibana 검증 파이프라인을 직접 셋업(개인 래퍼 포함)했습니다.

Background (S)

검증 역량이 SBL(대차)을 넘어 공매도 프로모션과 Trading(WTS 주문 PIP) 으로 확장됐습니다. 특히 Trading은 타 팀의 업무를 인계받아 단독으로 수행해야 했고, 기존에 쓰던 검증 도구(로그 레코더)만으로는 커버되지 않는 신규 도메인이었습니다.

Problem (T)

❶ 신규 도메인·단독 수행 — 익숙하지 않은 Trading 도메인을 혼자 QA 구조화해야 함 ❷ 검증 도구 공백 — 로그 레코더 CSV가 analytics 타입 이벤트를 캡처하지 못함 ❸ 배포 검증 — 공매도 프로모션 배포 후 퍼널 발화가 명세대로 쌓이는지 확인 필요

→ WHY 신규 도메인일수록 "명세와 실제가 다를" 위험이 크고, 기존 도구가 커버 못 하는 이벤트는 검증 사각지대가 됨 / HOW 인계 업무를 5대 점검으로 구조화하고, 알파 Kibana로 레코더가 못 잡는 analytics를 교차검증

Work Process (A)

01. Trading 주문 PIP 로그 QA (단독) — 인계받은 업무를 5대 점검으로 구조화, 레코더 CSV(1·2차+주문취소)와 알파 Kibana analytics 교차검증으로 대조. 이중 prefix 버그를 적발해 FE에 이슈레이징 → 수정 견인 → 재QA 통과. 명세(component 실측 반영, 미존재 기능 3건 삭제, step 추가) 갱신 + 진단 쿼리 8종·체크리스트 작성

02. 알파 Kibana 파이프라인 셋업 — 레코더가 못 잡는 analytics를 검증하기 위해 알파 Kibana API를 연결하고 개인 래퍼 스크립트로 영구 셋업

03. 공매도 프로모션(#6) 배포 헬스체크 — step별 view 단조감소 정상 확인, step-4 view 100% 발화 확인(이전 프로모션 ~40% 누락과 대조), 명세↔라이브 mismatch 8건 반영(명세 md + 모니터링 yaml 갱신). 퍼널 버전별 파라미터 키 상이(intro-v2 vs intro-v3)도 발견

04. 종목상세·매매 화면 이관 전수조사 & 라이브 재점검 — MTS 종목상세·매매 화면이 새 구조로 이관되면서 알파 로그를 6개 지면에 걸쳐 전수조사. 이슈 6건을 제보해 3건은 수정을 확인하고 3건은 재검증으로 종결. 알파에 이관 전·후 코드가 함께 떠 있어 host를 나누지 않으면 결론이 뒤집힌다는 것을 발견해 팀 가이드에 반영. 이후 주문 관련 4건을 라이브에서 재점검해 Kibana와 Impala 집계가 일치하고 주문 PIP의 이중 prefix가 해소된 것을 확인

Result & Insight (R)

▸ 실측 버그 적발 → FE 수정 견인: Trading 주문 PIP의 이중 prefix 버그를 잡아 코드 수정·재QA까지 연결 ▸ 검증 사각지대 해소: 로그 레코더가 못 잡는 analytics 타입을 알파 Kibana로 교차검증하는 경로를 새로 마련 ▸ 신규 도메인 단독 오너십: 인계 업무를 빠르게 구조화해 단독으로 QA·명세 갱신·인수인계서까지 완수 ▸ 배포 품질 확인: 공매도 프로모션의 핵심 step view 100% 발화를 검증해 퍼널 분석 신뢰성 확보 ▸ 알파 QA 기준 정립: 이관 전·후 코드가 공존하는 알파 환경에서는 host 분리가 필수라는 기준을 팀 가이드에 반영

🔗 연결 역량

  • 로그 QA·버그 적발 — 명세↔실측 대조로 이중 prefix 버그·mismatch 적발
  • 검증 인프라 구축 — 도구 한계를 발견하고 알파 Kibana 파이프라인을 직접 셋업
  • 신규 도메인 적응력 — 인계받은 낯선 도메인을 단독으로 구조화·완수
  • FE 견인 — 적발한 버그를 이슈레이징해 수정·재QA로 연결

Learning

검증 도구 자체의 한계(레코더가 못 잡는 이벤트 타입) 가 곧 검증 사각지대가 됨을 체감하고, 도구를 새로 붙여 사각을 메우는 것까지가 QA의 일임을 배웠습니다. 낯선 도메인도 "명세↔실측 대조 + 가설 기반 추적"이라는 같은 원칙으로 풀린다는 것을 확인했습니다.
